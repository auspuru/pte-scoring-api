# One-click student SWT exam reports — draft feature

**Scope:** Any Summarise Written Text question in AiryEmbrace, including the 43 November 2026 screenshots when those passages have been checked and imported. Nothing in this PR is deployed to Railway or merged to main.

## Student experience

- Beside each SWT passage, display a single **Report** button.
- A student clicks **Report** only if that exact question appeared in their real, official PTE exam.
- No numeric entry, form, questionnaire, or additional confirmation is required.
- After reporting, the button displays **✓ Reported** and cannot add another report.
- Report state is per signed-in student and persists in PostgreSQL. One student can contribute at most one report per question.
- NEW is an independent per-student status: it disappears only when the student **submits a practice response**, not when they report a real-exam encounter.
- Show the aggregate number **Reported by N students** beside each question, without exposing usernames. The November source-report mentions are a separate figure.

## Index sorting

1. Questions with at least one student report appear **before all questions without student reports**, across the entire SWT index.
2. Sort reported questions by the number of **distinct students** reporting them, highest first.
3. Within an equal number of student reports, follow previously configured source-report frequency ordering (for the November import batch), then existing legacy prediction order and stable original order.
4. The order is generated by the backend for **all users** in GET `/api/passages`, so the dropdown and study navigation share one source of truth.
5. After successful POST, the frontend immediately refreshes the authoritative question index and rerenders the list.
6. Each passage retains its original ID; practice drafts, submitted answers, scoring records and history stay keyed by their existing passage IDs.

## Storage and security

- Table: `swt_exam_question_reports`, primary key `(username,passage_id)`, columns `reported_at`, CASCADE references for account and passage cleanup.
- POST `/api/swt/exam-reports/:passageId`: requires a genuine signed-in session and a real passage ID. Uses `INSERT ... ON CONFLICT ... DO NOTHING` so duplicate clicks do not inflate counts.
- GET `/api/swt/exam-reports`: returns only aggregate counts and the current student's own boolean `myReported`.
- GET `/api/passages`: counts distinct students from the report table, prioritizes reported questions and preserves the existing source and legacy tie-breakers.
- No client-provided username or count is trusted. Rate limiting applies to report submission if Express rate-limit is available.

## Release gates

- Unit test coverage: duplicate report prevention, session authentication, per-student reporting, aggregation privacy, source-count ordering, reported question priority, stable IDs.
- Before any production launch: run full Node tests and release checks, verify PostgreSQL schema migration and browser interaction in a staging environment, and confirm the order in the student portal under multiple student accounts.
- The 43 missing passages are **not yet imported**: verify their transcriptions and reference answers first, and resolve incomplete screenshot tails.
- Do **not** merge to `main`, deploy Railway production, or modify existing student records without approval.
